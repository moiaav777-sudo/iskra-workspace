# Устройство

## Общая схема

```
браузер ──> шлюз (nginx на боевом; portal/scripts/dev_gateway.py в run.sh)
              │  auth_request  GET /auth/check/<сервис> ──> портал (кто вошёл, есть ли доступ)
              │  + X-Portal-User / -Role / -Name / -Team + X-Portal-Secret
              ├── /            портал        :8701   FastAPI, SQLite
              ├── /moderator/  Совещание     :8767   FastAPI, SQLite
              ├── /materials/  Материалы     :8971   FastAPI, файловое хранилище
              ├── /brief/      Бриф          :8932   свой HTTP-сервер на стандартной библиотеке
              ├── /a3/         Инфографика   :8941   FastAPI, SQLite
              ├── /theses/     Тезисы        :8961   FastAPI, SQLite
              ├── /transcriber/ Транскрибатор :8981  FastAPI, SQLite
              └── /profiles/   Объективки    :8991   FastAPI, SQLite
```

Каждый сервис — отдельное приложение со своей папкой, зависимостями, тестами и `CLAUDE.md`. Общего
кода нет, кроме модулей в `portal/shared/` (разговор с «Искрой», чтение документов, сверка чисел, ФИО),
которые копируются в сервисы скриптом `portal/scripts/sync_shared.sh`: правятся они только в
`portal/shared`.

## Вход и доступ

Портал хранит пользователей (PBKDF2, подписанный cookie сессии, второй фактор по желанию), роли
(`admin`, `employee`) и доступы к сервисам. Перед каждым запросом к сервису шлюз спрашивает портал;
сервис доверяет заголовкам `X-Portal-*` только при верном общем секрете `PORTAL_SECRET`, потому что
его порт доступен всем локальным процессам сервера. Администратор документы не создаёт и не правит,
его дело — пользователи, доступы, журнал, ключ «Искры» и наблюдение.

У сотрудника есть непосредственный руководитель; круг подчинённых уходит сервисам заголовком
`X-Portal-Team`, по нему списки делятся на «мои / отдела / все». Это фильтр показа, а не запрет;
модель целиком — `ACCESS-SPEC.md`.

## Журнал и сводка

Сервисы отправляют события в `POST /internal/audit` портала по `127.0.0.1` с общим секретом: кто, когда,
в каком сервисе, с каким объектом, сколько стоил вызов «Искры». По журналу портал строит сводку за месяц
и показывает администратору состояние сервисов.

## Хранение

Папка мероприятия живёт в «Материалах» (`STORAGE-SPEC.md`): дерево «год / месяц / дата название»,
документы с закреплёнными номерами (01 повестка, 02 участники, 03 модератор, 04 бриф, материалы с 05,
«(к вопросу N)» в имени), реестр 00 собирается сам, первичка в подпапке «Архив». Остальные сервисы
кладут туда готовые документы через `POST /materials/api/events/{id}/files` с полем `source`, по которому
новая редакция заменяет прежнюю. Пакет совещания — zip этой папки; своей сборки ни у кого нет.

Базы — SQLite у каждого сервиса в своей папке данных; документы «Брифа» — в его папке результатов.
Все пути задаются переменными (см. `CONFIGURATION.md`).

## «Искра»

Общий модуль `iskra_common.py`. Правила, проверенные живой пробой API:
- синхронный чат `POST /api/v1/chat` — ответ не дольше 90 секунд, годится для коротких вопросов
  (подсказчик портала, сверки);
- длинная работа (разбор документа, тезисы, расшифровка записи) — прогоны `POST /api/v1/runs` с
  `Idempotency-Key`, опрос результата `?after=next_after`, предел прогона 15 минут; файлы результата
  скачиваются по ссылкам из ответа (идентификатор файла одноразовый);
- `GET /api/v1/me` — проверка ключа и прав без расхода токенов; её использует «лампочка» портала;
- каждый вызов стоит порядка 50–110 тысяч токенов на вход независимо от длины вопроса — это особенность
  платформы, в сводке расход виден по сервисам;
- ключ живёт 7–365 дней, срок API не отдаёт: администратор вводит дату окончания в портале, портал
  предупреждает за неделю.

Ответы ИИ всегда проходят проверку схемы и сверку с источником (цифры, ФИО по реестру людей), и
человек подтверждает их перед тем, как они попадут в документ.

## Интерфейсы

Чистый HTML/CSS/JS без сборки. Палитра, шрифт и размеры — токены `portal/static/base.css`, его
подключают все сервисы первым; общая шапка — `portal/static/workspace-header.js`. Тема оформления
(«Искра» / синяя) переключается скриптом `portal/ops/apply_brand.sh`. Интерфейсные проверки идут в
node на настоящих файлах (`tests/js_*_check.js`), мобильные — в Chromium через playwright, если он есть.
