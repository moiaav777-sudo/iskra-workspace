# Портал — заметки для разработки

Общие правила пространства — в корневом `CLAUDE.md` (контракт сервисов, п. 5б — типографика и общая шапка),
памятка перед «Готово к выкладке» — `team/DEV-CHECKLIST.md`, устройство и выкладка — `portal/README.md`.

- Тесты: `portal/.venv/bin/python -m pytest -q portal/tests` (фронтенд — через `node`, если он есть в PATH).
- Поменяли стиль или скрипт в `static/` — проставьте версии: `portal/.venv/bin/python portal/scripts/stamp_static.py`
  (выкладка на VPS этого сама не делает).
- `static/workspace-header.js` и `static/base.css` подключают **все** сервисы: правка там видна везде сразу после
  выкладки портала. Ничего не ломайте в старом поведении шапки (имя, «А− А+», меню, выход).

## Уведомления

Решение пользователя 02.10: (А) общие объявления из админки, (Б) «Обновлено: …» после выкладки, (В) плашка
«Доступна новая версия» у открытой страницы, (Г) страница плановых работ; главное — **за минуту до выкладки во
всех сервисах красная полоса «Через 1 минуту будет обновление «<сервис>». Пожалуйста, приостановите работу и
сохраните текущий этап.»**, пауза 60 с, выкладка, затем зелёная «Обновлено: …». Telegram — нет.

**Каталог уведомлений** — `/opt/<work|meet>/notices` на VPS. Портал ищет его так: `PORTAL_NOTICES_DIR`
(`.env`), если задана; иначе каталог `notices` рядом с папкой портала (`BASE_DIR.parent / "notices"` — на VPS это
и есть `/opt/<work|meet>/notices`), если он существует; иначе `<portal>/data/notices` (стенд, тесты). Проверяется
на каждый запрос — каталог появляется при первой записи выкладки, перезапуск портала не нужен (ревью RC-22, К-1). Пишет только выкладка (`ops/vps-deploy-remote.sh`,
пользователь terra, каталог создаётся сам при первой записи, файлы 644), портал только читает; битый или
отсутствующий файл — «объявлений нет».

| Файл | Содержимое | Кто пишет |
|---|---|---|
| `current.json` | `[{id, kind, text, service, from, until, starts?, source: "deploy"}]`; `kind` — `info`, `warning`, `maintenance`, `update`; `service` пусто — все сервисы; `starts` — когда начнутся работы (отсчёт «через N с») | режим `notice` |
| `versions.json` | `{сервис: {commit, at}}` | режим `deploy` после удачного `/healthz` |

**Сервер** (`app/notices.py`, маршруты в `app/main.py`):
- `GET /api/notice` (за входом, как `/api/me`) → `{items, now}`: действующие (`from ≤ сейчас < until`) объявления
  из `current.json` и из таблицы `notices`; по важности (maintenance → warning → info → update), внутри — свежие.
- `GET /api/version` → `{versions, portal: {commit, at, started}}`.
- `GET/POST /api/admin/notices`, `DELETE /api/admin/notices/{номер}` — только администратор: текст до 500 знаков,
  вид по белому списку, «где» — все сервисы или один, срок — время в будущем или «до снятия». Повтор того же
  объявления (двойное нажатие) возвращает уже созданное, повторное снятие — не ошибка. В журнал — «Объявление
  добавлено» / «Объявление снято». Таблица `notices` заведена добавлением: старый код её не замечает, откат
  безопасен.
- Админка → вкладка «Объявления»: форма, список (объявления выкладки — только для чтения), кнопка «Снять».

**Общая шапка** (`static/workspace-header.js`) — сервисам ничего делать не нужно:
- полоса закреплена при прокрутке: в сервисах — внутри липкой `.ws-bar`, на страницах портала — сама липкая
  под `header.topbar`. info — акцент, warning — предупреждение, maintenance — красная с отсчётом, update — зелёная;
  текст плановых работ и «новой версии» переносится, остальные — в одну строку с многоточием. «Скрыть» запоминает
  id в `localStorage["ws-notice-hidden"]`, maintenance не скрывается. Объявление администратора «только для
  сервиса X» видно только в X (пустой `service` — везде); объявления выкладки видны во всех сервисах;
- опрос `/api/notice` сразу и раз в 30 с; скрытая вкладка не опрашивает, при возврате — сразу; на `/login` опроса
  нет. Полоса пересобирается только при изменении набора объявлений (фокус и экранный диктор не сбиваются);
- `/api/version` раз в 60 с: первый ответ — версия на момент открытия; сменился коммит **своего** сервиса —
  плашка «Доступна новая версия «…» — обновите страницу (сохраните несохранённое)» с кнопкой «Обновить».
  Свой сервис — по `data-service` (названия — словарь `SERVICE_IDS`, совпадает с `config.SERVICES`, тест сверяет),
  `data-service-id` — явный id, иначе по префиксу адреса; страницы портала — `portal`;
- ошибки и 401 — молча, показанное остаётся (портал сам может перезапускаться). Стили вставляются из скрипта и
  берут переменные `base.css`, размеры в rem, на телефоне — одна строка с многоточием.

**Выкладка** (`ops/`):
- `ship.sh <RC> <сервис>=<коммит>… --note "что изменилось" [--now] [--plan]`: срез before → `vps_notice work
  <сервис|all> maintenance 3 "Через 1 минуту будет обновление «…»…"` (несколько сервисов — одно объявление `all`
  с перечнем, срок 1 + 2·N мин) → `sleep 60` (`--now` — без паузы и с текстом «Сейчас будет обновление…») →
  выкладка по порядку → `vps_notice … update 1440 "Обновлено: «…» — <--note>"` (без `--note` — «Обновлён сервис
  «…»»). Не ушло предупреждение — выкладка не начинается. `--plan` печатает тексты и ничего не делает.
- `deploy_transport.sh` → `vps_notice <work|meet> <сервис|all> <kind> <минут> <текст> [секунд до работ]`:
  цель, сервис, вид и числа проверяются по белым спискам до сборки ssh-строки; ssh — тот же remote-скрипт; облако — workflow `deploy.yml`, `mode=notice` с inputs `text`, `kind`, `ttl_min`,
  `lead_s`. Текст до VPS идёт в base64 (ssh склеивает аргументы в строку для удалённой оболочки).
- `vps-deploy-remote.sh`: `notice` — добавить объявление `deploy-<время>-<мс>-<случайное>`, снять просроченные;
  `maintenance` и `update` снимают прежние maintenance того же адресата, `update` — ещё и прежнее `update` того
  же адресата (зелёные строки не копятся). `deploy` после `/healthz` — версия в `versions.json`
  и снятие maintenance этого сервиса (сбой записи выкладку не роняет). `deployed` — то же без выкладки
  (ручной ремонт). Проверка на копии: `NOTICES_DIR=/tmp/x bash ops/vps-deploy-remote.sh work moderator - notice
  info 5 "$(printf 'текст' | base64)"`.

**Страница плановых работ** — `ops/down.html`: самодостаточная (стили и скрипт внутри — сервис в эту минуту не
отвечает), «Сервис временно недоступен»; если портал жив и есть объявление maintenance — показывает его текст,
«обновите страницу через минуту» и сама перезагружается через 60 с; кнопка «Попробовать снова». **На VPS её ставит
сессия сервера:** `/var/www/work-portal/_down.html` (тот файл, который nginx отдаёт на 502/503/504); после правки
`down.html` — попросить сессию сервера переложить.
