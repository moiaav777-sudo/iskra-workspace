# Бриф из справки — чат сервиса

Этот чат отвечает только за папку `brief/`. Общие правила и контракт с порталом описаны в `../CLAUDE.md`, открытые задачи — в `../TRACK.md` → «Бриф».

## Что это

Справка DOCX превращается в бриф DOCX: «История», «Текущий статус», «Проблематика», «Варианты решения». «Искра» только достаёт факты с дословными цитатами. Программа сверяет их с исходными документами, сама считает и собирает документ. Неподтверждённое подсвечивается жёлтым; в проблематику и варианты решения нового брифа сразу входят все предложения из справки, куратор оставляет нужные и правит формулировки.

Видов брифа два (`BRIEF_TYPES` в `app/server.py`):

- **Бриф для региона** — по сводной справке о развитии региона, одна справка на задание, анкета с заранее известными полями (`app/prompt.md`, `app/build_brief.py`).
- **Общий бриф** — по любой теме: к справке прикладываются статья, обращение, письма ведомств, несколько документов на задание. Разделы свободные, у каждого факта — цитата и имя файла, откуда она взята (`app/prompt_topic.md`, `app/build_topic.py`).
- **Саммари докладов** — по докладам выступающих, по документу на каждого (Word, презентация или PDF). На выходе документ Word: первая страница — оглавление, дальше по странице на доклад (`app/prompt_summary.md`, `app/build_summary.py`). Вёрстка взята из «Повестки»: A4, поля 2/1,5/2/2 см, Times New Roman 14, интервал 1,15, номер страницы сверху со второй. ФИО, должность и тему нейросеть достаёт из докладов, человек правит их на экране и пересобирает документ.

- **Сводный бриф** — 2–10 брифов одним документом с содержанием по названиям вопросов (`app/build_joint.py`, «Результаты/Сводные»; предел `JOINT_MIN, JOINT_MAX` в `server.py`, в `ui.html` тот же). Из реестра — отметить брифы галочками, «Свести в один»: брифы пересобираются из своих фактов. **«Объединить брифы»** — кнопка в шапке рядом с «＋ Новый бриф» (`#merge-open`; пользователь 05.10 не нашёл прежнюю ссылку под списком): окно с зоной перетаскивания (несколько .docx сразу, файл, брошенный в окно, не проваливается в справку), справа порядок — номер, имя файла, ↑/↓, перетаскивание строк, «Убрать»; файлы уходят в `api/joint-files` в этом порядке и переносятся как есть, меняется только номер вопроса; названия вопросов сервер читает при сборке, они видны в готовом сводном. Пределы: файл 15 МБ, все вместе 40 МБ (`MERGE_TOTAL_BYTES`, тело ≈53 МБ — под 55 МБ nginx портала). Чужой файл, 11-й бриф — понятная причина, а не 500. Проверка без образцов: `python -m pytest -q tests/test_merge_limit.py` (10 брифов из `legacy-console/примеры`, 11 — отказ; node-проверка окна `tests/js_merge_dialog_check.js`).
- **Объединение понимает файл с несколькими брифами** (пользователь 13.10: «в документе уже 10 брифов — должен появиться 11-й»; до этого документ на 13 вопросов вклеивался целиком со своим заголовком и оглавлением, номер получал только первый вопрос). `build_joint.read_briefs` делит файл по таблицам «Вопрос / …»: вопрос — его таблица и всё до следующей (хвост из пустых абзацев и разрывов страниц срезается), шапка файла до первой таблицы (заголовок, своё оглавление) в сводный не идёт, ссылки «К оглавлению» на неё и на `_top` ведут к содержанию сводного, у вопроса без такой ссылки она добавляется. Номера сквозные по всем файлам; автонумерация Word у заголовка вопроса (`<w:numPr>`, нумерация стиля) снимается — иначе рядом с нашим «n. » стоял бы ещё и свой «1.». Чужие стили с теми же номерами, что в шаблоне, но другим определением (`1`, `a7`, `31` раздаются каждым Word заново) переносятся под именами `M<n>…` — бриф выглядит как в файле, а не как «Plain Table 3» шаблона (шапка заглавными); стили «по умолчанию» (`w:default="1"`, «Обычный») — всегда шаблонные, иначе второй «по умолчанию» перекрасил бы весь сводный; стили и списки переносятся один раз на файл (не на вопрос), `styles.xml`/`numbering.xml` сводного ограничены `MAX_STYLES` (ревью RC-2026-10-13-4). Хвост вопроса (пустые абзацы, разрывы) срезается только после таблицы. Пределы: `JOINT_MAX` файлов за раз и `JOINT_MAX_QUESTIONS` вопросов в сводном (`server.py`). Проверка: `tests/test_merge_limit.py` (05–07) — вложенный сводный, ручной документ с нумерованным заголовком и `_top`, предел.
- **Номера страниц в оглавлении** (сводный, саммари) — числа в самом файле (`app/pages.py`): прикидка при сборке, сверенная с Word; с `BRIEF_PAGES=word` (только после проверки общим треком) Word уточняет их в фоне, на копии, со сроком 20 с. `updateFields` не ставится. Из прикреплённых брифов переносятся только внутренние поля Word (PAGEREF, REF, PAGE, TOC, HYPERLINK \l) — у остальных остаётся текст результата.
- **«История» и «Текущий статус» правятся на экране** (просьба пользователя 27.09): правка сохраняется сама, как проблематика. У брифа для региона факты не трогаются — правки лежат в `факты.json` → `edits` и привязаны к тексту собранного абзаца (`build_brief.apply_edits`); у общего брифа блок и есть данные, правленый блок помечается `manual` и с документами не сверяется. Текст абзаца в `edits`/блоке — строка с возможными вставками `<strong>…</strong>`; на сервере её разбирают `build_brief.human_parts`/`human_plain` в прогоны для DOCX (`<w:b/>`), общие для обоих видов брифа. Изменение одной только разметки (без смены слов) тоже правка — иначе выделение терялось бы при пересборке.
- **Единый формат блоков** (решение пользователя 13.10: «каждый раздел — отдельным блоком для форматирования, как в модераторе; единый формат; все делаем одинаково»). Раздел `#sec-text` — карточки общего компонента `WorkspaceBlocks` (`/static/blocks.js`, `blocks.css`, Quill и DOMPurify отдаёт портал, контракт — шапка `portal/static/blocks.js`): «История», «Текущий статус» (с 14.10 — отдельными карточками, см. ниже), «Проблематика», «Варианты решения». Нажатие на блок открывает общий редактор с общей панелью, как сценарий «Совещания»; прежний список абзацев с кнопками «¶ • H», «Ж», «×», «↺», «+ абзац», своя копия `app/vendor/` и маршрут `/vendor/` убраны.
  *Почему контракт с сервером не менялся:* `/api/rebuild` по-прежнему принимает абзацы `[{text, kind, orig, i}]`. Блок строится из абзацев раздела (`sectionHtml`: обычный — `<p>`, пункт — `<li>` в общем `<ul>`, заголовок — `<h3>`; у правленого — его `<strong>`, у собранного — экранированный текст; убранные в блок не входят). Сохранённый блок разбирается обратно (`parseSectionHtml`: `li` → пункт, `h1–h6` → заголовок, остальное → обычный; внутри — только текст и `<strong>`) и сопоставляется с прежними абзацами (`mergeSection`): точное совпадение по словам — тот же абзац; между совпадениями несовпавшие новые и прежние — пары по порядку, при неравном числе — по общим словам: это правка (orig/i прежние); оставшиеся прежние — убраны (`text ""`, orig/i сохранены), оставшиеся новые — добавлены (без orig и i). Иначе правка в блоке выглядела бы как «всё убрали и написали заново»: у брифа для региона пропала бы привязка правок к собранному тексту, у общего — цитаты. `collectSections()` отдаёт это состояние (`state.sections`), а не читает страницу.
  *Что идёт в Word:* только вид абзаца (обычный · пункт списка · заголовок) и полужирный. Курсив «Истории» и синие скобки «Текущего статуса» — правило всего блока (`Doc.styled`/`with_parens`); прочее оформление панели (курсив, цвет, ссылки, выравнивание) при сохранении снимается, текст остаётся, и блок после сохранения показывает ровно то, что уйдёт в документ. Сервер снимает чужую разметку ещё раз (`clean_sections`: всё, кроме `<strong>`/`<b>`). Смена вида у собранного абзаца брифа для региона — тоже правка: `apply_edits` отдаёт `orig_kind` (вид собранного абзаца), `edits_from_sections` сравнивает с ним и кладёт в правку `kind` (до 13.10 вид собранного абзаца молча возвращался).
  «Вернуть текст из справки» — действие карточки: у брифа для региона — собранный текст и вид, добавленное убирается; у общего брифа остаются несобранные человеком блоки, правленые и добавленные убираются (исходного текста у них уже нет). Только чтение — администратор (документы не ведёт, решение 19.09), роль `chief` и бриф коллеги, открытый вам на «смотреть» (окно «Доступ»). Открытый редактор принадлежит одному брифу (ревью RC-2026-10-13-8, К-1): id блоков — `history:<папка>`/`status:<папка>`/`problems:<папка>`/`solutions:<папка>`, иначе `update()` компонента перенёс бы редактор с набранным в другой бриф; перед сменой брифа («История», ссылка `#job=`, «Новый бриф», «Сделать заново») несохранённая правка — вопрос «уйти без сохранения?», а набранное, выпавшее из редактора мимо вопроса (бриф стал «смотреть», сервер начал новое задание), — плашка «Ваш текст не сохранён» своего брифа: вернуть в редактор, скопировать, отбросить (`onEditLost`). Проверка без образцов: `python -m pytest -q tests/test_sections_blocks.py` (`node tests/js_sections_blocks_check.js app/ui.html ../portal/static` — настоящий ui.html в Chromium).
- **Четыре отдельные карточки** (решение пользователя 14.10: «История», «Текущий статус», «Проблематика», «Варианты решения» — каждая отдельным модулем-блоком, визуально разделены). В `#sec-text` один `WorkspaceBlocks.mount` с четырьмя карточками (`history`, `status`, `problems`, `solutions`), в каждой один блок (`org`, `report`, `problem`, `decision`), между карточками отступ; над ними одна короткая подсказка. Прежние галочки кандидатов (`#list-sig`, `#list-sol`), поля «Своя формулировка» и «Варианты решения», `#sec-prob` убраны. У «Истории»/«Текущего статуса» своё «Вернуть текст из справки» (сбрасывает только свой блок). У брифа без абзацев разделов (старые) — только карточки проблематики и решений; у саммари карточек нет.
  *Откуда содержимое «Проблематики»/«Вариантов решения»:* блок — ровно `result.problems`/`solutions` (плоские строки, как в документе: один пункт — абзац, несколько — список, строка с двоеточием в конце — вводная без маркера, `build_brief.listed`). **Все предложения новый бриф получает на сервере при первой сборке** (`finish_build` → `fill_from_signals`: фактов ещё нет, выбора нет — `problems = signals`, `solutions = solution_signals`, `ui_selection = {picks: [], own, sol_picks: [], sol_own}`, документ собирается сразу с ними; предложения брифа для региона считает сама сборка, поэтому документ собирается второй раз). **Экран при открытии ничего не сохраняет** (ревью RC-2026-10-14-1, К-1/К-2: автозаполнение с экрана переписывало готовые брифы «Отсутствует» при первом открытии кем угодно и могло записать в бриф, открытый на «смотреть»). «Сделать заново» сохраняет прежнюю проблематику как есть (и пустой сохранённый выбор тоже); готовые брифы до 14.10, где куратор ничего не отметил, остаются «Отсутствует» — предложения в них вносит только действие «Все предложения из справки»/«Все варианты из справки» (с подтверждением; закрывает редактор своего блока, текст блока заменяется). Сохранение блока: каждый абзац/пункт/заголовок — одна строка, только текст, пробелы схлопнуты, пустые выброшены; строка, чьи слова совпали с прежним пунктом, отдаётся прежней строкой как есть (`keepListLines`: редактор показывает неразрывный пробел обычным, без этого «Сохранить» стирал бы его во всех пунктах, а «Сохранить» без правки слал бы запрос и писал в журнал — Н-1).
  *selection теперь всегда own:* экран шлёт `{picks: [], own: problems, sol_picks: [], sol_own: solutions}`; контракт `/api/rebuild` и `clean_selection` прежние, галочки по номерам у старых брифов сервер принимает, экран показывает их текущий текст (`problems`) и после первого сохранения пишет его в `own`. Пределы `clean_lines` подняты до 200 пунктов по 4000 знаков (`LINES_MAX`, `LINE_CHARS`): весь выбор идёт одним списком, у брифа для региона предложений бывает больше полусотни. Рядом с `sol_own` сервер хранит и пустой `sol_picks: []`. **Откат на экран до 14.10 (известное, Н-3):** старый экран покажет весь выбор как «свои формулировки» без галочек — это нормально; старый сервер (`clean_lines` 50 × 2000) при первом сохранении после отката молча срежет проблематику длиннее 50 пунктов (в журнале — «убрано»); у брифов, сохранённых до появления `sol_picks: []`, старый экран сопоставит решения с кандидатами по тексту и переставит их (вводная с двоеточием уедет вниз). Тело запроса на самих пределах (≈6 МБ) больше `json_body` 5 МБ — на практике недостижимо (Н-9). «Правила из правок» смотрят только на абзацы разделов — от пустых `picks` не зависят. Счётчик «✓ В брифе: N проблем · M вариантов» — по пунктам блоков. Нажатие на другой блок при несохранённой правке — подсказка «Сначала сохраните или отмените правку в блоке «…»» (компонент второй редактор не открывает). Проверка: `tests/js_sections_blocks_check.js`, `tests/test_sections_blocks.py`.
- **Правила дообучаются от правок** (`app/lessons.py`, решение пользователя 27.09): после серии правок (60 с тишины) разница «было → стало» уходит нейросети отдельным вызовом — разовая фактическая поправка или общий урок формата/стиля. Урок общего действия становится **предложением** на странице брифа (раздел «Правила из правок») и дописывается в правила вида брифа только после «Принять»; принятое отзывается там же одним нажатием (ревьюер RC-2026-09-27-1, К1). Правки уходят судье как данные в JSON, правило-команда («игнорируй правила…») отбрасывается. `prompt*.md` в коде не трогаются: журнал уроков — `<BRIEF_HOME>/Правила/уроки.json`, правила прогона = `prompt*.md` + принятые уроки (`lessons.compose`). Дубликат и противоречие не применяются, а записываются в журнал. С консоли: `python3 app/server.py --lessons`, `--revoke-lesson <id>`. Приём из «Приёмной» (`POST /api/intake`): автор задания — вошедший человек, заголовком его не подменить (К2). Расход этого вызова — в журнал портала («Урок из правки брифа»).

## Работа

```bash
../portal/.venv/bin/python -m pytest -q tests      # 130 тестов: нужны образцы справок в ~/Downloads;
                                                   # BRIEF_PAGES=word — ещё и сверка номеров с PDF от Word (Mac)
bash ../portal/scripts/dev_stack.sh                # через портал: http://127.0.0.1:8080/brief/
BRIEF_HOME=$(mktemp -d) python3 app/server.py      # отдельно, без портала
# выкладку делает общий трек: напишите в ../TRACK.md → «Готово к выкладке»
```
