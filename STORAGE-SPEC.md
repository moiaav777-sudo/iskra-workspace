## Правила переименования

```
00. Реестр материалов.docx          собирает сервис
01. Повестка.docx                   из «Повестки»
02. Список участников.docx          из «Повестки»
03. Модератор_<тема>.docx           из «Модератора»
04. Бриф.docx                       из «Брифа»
05…  материалы: по возрастанию номера вопроса,
     внутри вопроса — в порядке добавления
NN.1 приложение/уточнение к материалу NN
```

- Суффикс `(к вопросу N)` ставится, когда у мероприятия есть повестка с нумерованными вопросами. У мероприятий без повестки («Бриф по ЯНАО») суффикса нет.
- Название берётся из самого документа (заголовок, «Справка о …»), а не из имени файла. Запасной вариант — очищенное имя файла: подчёркивания в пробелы, снять `v5`, `(2)`, хвосты дат.
- `Архив/` и `пдф/` не нумеруются и в реестр не попадают.
- 01–04 — забронированные номера. Пока документа нет, номер просто пустует, и в реестре видно, чего не хватает.

## Как это выглядит в работе

1. **Завёл мероприятие** — дата, название, направление. Папка создана, 01–04 забронированы.
2. **Бросил пачку файлов** одним движением. Сервис читает каждый и показывает один экран: слева файл, справа предложенное название и «к какому вопросу». Правите что нужно — «Применить». Всё переименовано и пронумеровано разом.
3. **Повестка, Модератор, Бриф, Тезисы кладут свои документы прямо в эту папку** под номерами 01–04 — не в архив на скачивание, а в папку.
4. **`00. Реестр` пересобирается сам** при каждом изменении.
5. **Скачать** — папку целиком одним архивом или отдельный файл.

Главное, чего Яндекс не умеет: **текст документов уже извлечён**, поэтому мероприятие ищется по фразе внутри вложенного файла, а не только по имени папки. Это и есть «быстро добираться до нужной папки».

## Решено (20.09.2026)

1. **Старое не переносим.** Хранилище начинается с чистого листа: в нём живут только документы,
   которые складываются к новым совещаниям. 391 старая папка остаётся на Яндексе как есть.
   Понадобится — перенесём потом по одной; спешить незачем.
2. **Папка монтируется в проводник (WebDAV).** Word открывает и сохраняет файл прямо в хранилище,
   как сейчас с Яндексом. Браузерный вид остаётся для раскладки, реестра и поиска.
3. **Холодная копия — Яндекс.** Ночное зеркало папки хранилища. Подписка уже есть, докупать нечего.
   VPS остаётся только туннелем и местом для копий баз.

## Порядок работ

**Шаг 1. Сервис «Материалы», порт 8970 — папка мероприятия.**
Дерево `Направление / год / месяц / мероприятие` на ПК. Карточка мероприятия в портале:
загрузил файлы — сервис прочитал каждый, предложил человеческое название и вопрос, расставил
номера, собрал `00. Реестр материалов.docx`. Поиск по тексту внутри документов — по контракту
`GET /api/search`, как у остальных сервисов. Здесь появляется вся польза; дальше — удобство.

**Шаг 2. Связка с сервисами.**
«Повестка» кладёт в папку `01. Повестка.docx` и `02. Список участников.docx`, «Модератор» —
`03. Модератор_<тема>.docx`, «Бриф» — `04. Бриф.docx`. Пакет к совещанию (`portal/app/package.py`)
перестаёт собираться по кускам из пяти сервисов и просто отдаёт папку.

**Шаг 3. Сетевой диск.**
WebDAV поверх того же дерева. Для диска — отдельный пароль приложения, не пароль от портала:
проводник Windows умеет только Basic-проверку, и светить им основной пароль незачем.
Файл, бро­шенный в папку мимо портала, остаётся без номера — сервис показывает его как «нужно разложить».

**Шаг 4. Холодная копия на Яндекс.**
Ночное зеркало и строка в отчёте резервного копирования рядом с базами.

## Что учесть на шаге 3

- Проводник Windows по умолчанию не открывает по сети файлы тяжелее 50 МБ — правится одной
  настройкой реестра на ПК. Для docx неважно, для больших презентаций — важно.
- Весь обмен идёт через домашний канал ПК. Документы (в среднем 400 КБ) летают незаметно,
  стомегабайтная презентация из дома наружу будет открываться заметно дольше, чем с Яндекса.
- WebDAV пишем не руками: у проводника Windows капризный клиент (PROPFIND, LOCK). Берём `wsgidav` —
  зрелая библиотека на чистом Python. Это первая внешняя зависимость такого рода, поэтому решение
  записано здесь.

## Чего делать не стоит

Переписывать Яндекс.Диск целиком — синхронизация, мобильное приложение, публичные ссылки,
дедупликация. Это отдельный продукт. Умное здесь — раскладка и реестр; хранение само по себе
ценности не добавляет.

## Осторожно

Переименование и перенос — только после показа «было → стало» и подтверждения; исходные имена
пишутся в журнал, откат одной кнопкой. Чужие старые папки сервис не трогает вовсе.

## Приёмная: как документы попадают в хранилище

98 % документов приходит в мессенджере MAX, в том числе с телефона. Решение от 20.09.

**Общая часть для любого канала — «Приёмная».** Прилетевший документ не знает, к какому мероприятию
он относится. Поэтому он падает в общую папку вне мероприятий и **сразу читается**: текст, предложенное
название, узнанный вид («похоже на повестку»). В портале — лента «Пришло», у каждого документа кнопка
«В мероприятие…» со списком ближайших и «Новое мероприятие». Плюс режим «активное мероприятие»:
выбрал одно — и присланное падает в него без вопросов. Это же закрывает мысль про «папки-склады
без совещания».

**Канал для iPhone — Быстрая команда.** Портал выдаёт в профиле личный **ключ приёмной**; быстрая
команда «Материалы» показывается в меню «Поделиться» и шлёт файл на `POST /materials/api/inbox`
с этим ключом в заголовке. Ключ только загружает и ничего не читает; потерялся телефон — отозвали
ключ в профиле. В nginx для этого адреса отдельный раздел без проверки cookie: ключ проверяет сам
сервис. Первым делом проверяем, что «Получить содержимое URL» умеет слать файл формой — если нет,
запасной вход ниже.

**Договор о приёмке (сделано порталом 20.09).**

```
POST /materials/api/inbox
  заголовок  X-Inbox-Key: <ключ приёмной>      ключ в заголовке, не в адресе:
                                               адреса попадают в журнал nginx, заголовки — нет
  тело, способ 1  multipart/form-data, поле files (можно несколько),
                  необязательное поле event — id мероприятия, если телефон его знает
  тело, способ 2  документ целиком телом запроса, имя — заголовком X-Inbox-Name
                  или из Content-Disposition
```

Второй способ появился 20.09 из-за телефона: в «Быстрых командах» файловое поле формы собирается
не всегда — телефон требует выбрать у файла текстовое свойство и отправляет строку с именем вместо
документа. Спорить с телефоном бессмысленно, поэтому приёмка берёт документ и так, как он умеет
наверняка. В команде это одна настройка: «Тело запроса: Файл», значение — «Входные данные команды».

Сервис «Материалы» проверяет ключ у портала:

```
GET http://127.0.0.1:8700/internal/inbox-user?key=<ключ>
  заголовок X-Portal-Secret: <общий секрет>
  → 200 {"login", "role", "name", "team"}   ключ годен, доступ к «Материалам» есть
  → 404                                      ключ не подошёл, отозван, у человека нет доступа
```

**Важно:** `/api/inbox` должен идти мимо общей проверки `portal_gate` — так же, как `/healthz`.
Иначе middleware отклонит запрос раньше, чем сервис посмотрит на ключ: сейчас так и происходит,
боевой адрес отвечает 401 «Нужен вход через портал».

Второй адрес — чтобы команда на телефоне показала человеку список и он выбрал прямо там:

```
GET /materials/api/inbox/events
  заголовок  X-Inbox-Key: <ключ приёмной>
  → {"items": [{"id", "title", "date"}]}   ближайшие мероприятия, сверху ближайшее
```

В nginx раздел объявлен префиксом (`^~ /materials/api/inbox`), поэтому оба адреса идут мимо
проверки cookie. Оба проверяют ключ одинаково.

Дальше сервис работает так, будто человек пришёл обычным путём с заголовками `X-Portal-*`.
Ответ на загрузку: `{"ok": true, "saved": ["имя файла"], "where": "Приёмная"}` — или название
мероприятия, если в поле `event` пришёл его id.

Портал уже умеет: колонка `inbox_key` у пользователя, выдача и отзыв ключа в «Моём профиле»
(только сотруднику — администратор документы не ведёт), `GET /internal/inbox-user`, отдельный
раздел в nginx без проверки cookie с ограничением 60 запросов в минуту с адреса.
Отзыв ключа и снятие доступа к «Материалам» выключают приёмку мгновенно.

**Быстрая команда на iPhone — как собирать.** Делаем в два захода, чтобы не построить всё на
непроверенном. Сначала простая: отправляет документ в приёмную и показывает ответ.

1. «Команды» → `+` → назвать **Материалы**.
2. В настройках команды включить **«Показывать в меню „Поделиться“»**, тип входа — файлы
   и документы.
3. Действия:
   - **Получить содержимое URL** → `https://workspace.example.ru/materials/api/inbox`,
     метод `POST`, заголовок `X-Inbox-Key` = ключ из «Моего профиля»,
     **тело запроса — «Файл»**, значение «Входные данные команды»
     (форму с полем `files` телефон собирает не всегда — см. договор выше),
     плюс заголовок `X-Inbox-Name` с именем файла, если хотите сохранить исходное имя.
   - **Показать уведомление** с ответом — чтобы было видно, что документ принят и как он назван.

Вторым заходом добавляем выбор мероприятия через `GET /materials/api/inbox/events`. Проверять это
надо на живом телефоне: как «Быстрые команды» показывают список из ответа сервиса, снаружи не
угадаешь. Поэтому `/events` в договоре есть, а в рецепте появится после проверки.

**Запасной вход — папка на Яндекс.Диске.** «Поделиться → Яндекс.Диск → Входящие»: ПК уже
синхронизирует диск, сервис смотрит в условленную папку. Работает на любом телефоне и сегодня,
минус — лишний шаг и задержка синхронизации.

**Бот в MAX — решено не заводить (20.09).** У пользователя нет ни самозанятости, ни ИП, ни
организации, а ботов в MAX, по сторонним данным, заводят только верифицированные юрлица.
Регистрировать бота на ИП супруги отказались, и по делу: бот был бы её — её организация в карточке,
её ИП закроется — бот умрёт, «перевести» бота другому владельцу нельзя (это новый бот с новым ником
и токеном). Единственное, чем бот был лучше быстрой команды, — выбор мероприятия кнопками в чате;
команда на телефоне делает то же самое через `GET /materials/api/inbox/events`. Возвращаемся к боту
только под задачу, которой команда не решает, — например, чтобы документы присылал коллега.

**Бот в MAX — что про него известно, если вопрос вернётся.** У MAX есть Bot API: принимает файлы до 4 ГБ, умеет длинный опрос,
то есть работает прямо с ПК без реле через VPS (в отличие от Telegram). Но создавать ботов, по
сторонним данным, могут только верифицированные юрлица РФ — официальная документация об этом
молчит, проверяется через `@MasterBot` командой `/create`. Заведётся — бот станет самым коротким
путём: переслал документ, выбрал мероприятие кнопкой. Приёмная к тому моменту уже будет готова
его принять.

## Поток по одному и версии документов (замысел от 20.09)

Материалы приходят не пачкой к совещанию, а по одному и в течение нескольких дней. Отсюда две
задачи, и обе решаются тем, что уже есть.

### Куда положить, если документ прилетел один

Спрашивать «к какому совещанию?» на каждый документ — это десять вопросов за день. Поэтому
**не спрашиваем, а сообщаем и даём поправить**:

- у человека есть **активное мероприятие** — он выбирает его один раз кнопкой «Складывать сюда»
  на карточке мероприятия (или из списка в команде на телефоне);
- присланный документ падает туда сразу, а телефон показывает: «Принято: *Позиция Минстроя
  России* → Совещание по детям-сиротам»;
- **активное мероприятие живёт сутки.** Просрочено — документ ложится в «Приёмную», и команда
  говорит об этом прямо. Так документ не улетит в позапрошлое совещание, о котором человек забыл;
- в «Приёмной» сервис **подсказывает**, куда это похоже: сравнивает текст и даты с ближайшими
  мероприятиями. Подсказка, а не решение: кнопка «В мероприятие…» рядом.

### Несколько версий одного документа

Сервис сравнивает пришедшее с тем, что уже лежит: точная копия (совпал хеш), то же имя файла
после очистки, то же предложенное название, сильно пересекающийся текст.

| Что нашлось | Что делает сервис |
|---|---|
| точная копия | ничего не меняет и говорит «это уже есть» — вопроса человеку нет |
| похоже на лежащий документ | помечает в ленте «Пришло»: «похоже на *06. Позиция Минстроя России*» и даёт три кнопки |
| ни на что не похоже | кладёт обычным следующим номером |

Три кнопки — это ровно то, что просил пользователь, и обе первые уже описаны правилами нумерации:

- **Заменить** — новый файл встаёт на место старого, **номер и название сохраняются**, прежняя
  версия уезжает в `Архив` (там и так лежит первичка) с датой в имени. В реестре — только
  актуальная версия. Ссылки и номера в переписке не ломаются, а прошлую версию всегда можно достать.
- **Дополнить** — документ получает номер `NN.1`, то есть встаёт приложением к `NN` и наследует
  его вопрос. Это уже работающее правило («13.1. Предложения Минстроя России»).
